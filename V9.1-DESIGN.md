# Raspberry Pi 2B Fedora 36 / Diretta Kernel V9.1

## Objective

V9.1 keeps the Fedora Linux 6.2.15 source and the existing Fedora SRPM patch
as its base. It selectively backports the Raspberry Pi 2B hardware support
that is absent from the Fedora/upstream source tree used by V9.

Target release remains:

`6.2.15-215.fc36.armv7hl`

The original Diretta modules remain unchanged:

- `alsa_bridge.ko`
- `diretta_direct.ko`

## Why V9.1 is needed

The V9 and V10 `bcm2709_defconfig` files were compared and are byte-for-byte
identical. The important difference is source support, not the defconfig.

The Raspberry Pi Linux 6.2.16 tree used by V10 contains the downstream
`USB_DWCOTG` host controller driver and its FIQ integration. The shared
defconfig requests `CONFIG_USB_DWCOTG=y`, but the Fedora 6.2.15 source used
by V9 does not contain that driver. V9's `olddefconfig` therefore discards
the unsupported option. V9 then relies on the upstream `DWC2` path instead
of the Raspberry Pi downstream USB Host path.

V10 also builds the LAN9514 network path into the kernel:

- `CONFIG_USB_DWCOTG=y`
- `CONFIG_USB_USBNET=y`
- `CONFIG_USB_NET_SMSC95XX=y`
- `CONFIG_USB_STORAGE=y`

V9's original fragment made USB networking and storage modules. V9.1 aligns
these hardware-critical options with V10 so enumeration does not depend on
late module autoloading.

## Source provenance

- Fedora base source: Linux 6.2.15 from the verified Fedora 36 SRPM/source inputs
- Upstream Linux 6.2.15 base commit:
  `3c6c5ba197a9daf02c77ae39d65677c5e63e0845`
- Raspberry Pi reference commit:
  `4c7938b86db7dfccbfd4d2a840091cbb7fbf2e9f`
- Raspberry Pi source version: Linux 6.2.16
- V9.1 does **not** replace the Fedora source tree with the Raspberry Pi tree.

At build time, the workflow generates a narrow Git diff from the exact
upstream 6.2.15 base to the pinned Raspberry Pi commit, limited to the
following hardware support:

1. BCM2835 FIQ architecture support and ARM FIQ entry/restore code
2. Raspberry Pi DWCOTG USB Host driver and its common portability library
3. BCM2835 mailbox early initialization
4. Raspberry Pi firmware initialization ordering
5. BCM2835 clock initialization ordering
6. BCM2835 early USB register mapping used by the FIQ path

The patch is checked with `git apply --check` before it is applied. Any
context conflict stops the build; the workflow does not force-apply hunks.

The following were deliberately excluded from this first backport:

- experimental SMSC95XX turbo-mode and packet-size defaults
- optional MAC-address override behavior
- unrelated Raspberry Pi camera, display, audio-HAT and other-board drivers
- the full Raspberry Pi kernel source tree

The generic upstream SMSC95XX driver remains in use, but is built in together
with USB networking. If the V9.1 hardware test later shows a specific PHY,
MAC-address or link problem, those network-driver changes can be evaluated
separately rather than bundled into the USB Host repair.

## Configuration requirements

In addition to V9's original Fedora root and Diretta requirements, V9.1
requires:

- `CONFIG_USB_DWCOTG=y`
- `CONFIG_FIQ=y`
- `CONFIG_USB_USBNET=y`
- `CONFIG_USB_NET_SMSC95XX=y`
- `CONFIG_USB_STORAGE=y`
- `CONFIG_RASPBERRYPI_FIRMWARE=y`
- `CONFIG_BCM2835_MBOX=y`
- `CONFIG_CLK_RASPBERRYPI=y`

`CONFIG_USB_DWC2=m` is retained. The DWCOTG driver is built in and is not
expected to appear in `lsmod`.

The exact kernel release, vermagic, zero-CRC exports and undefined-symbol
checks for the two original Diretta modules remain as in V9. These are
static checks only; successful runtime loading on the actual Pi 2B is still
required.

## Acceptance test

After backing up the SD card and installing the complete V9.1 package:

1. Confirm Fedora 36 boots and mounts the existing ext4 PARTUUID root.
2. Confirm USB host enumeration with `lsusb`.
3. Confirm the LAN9514 hub and SMSC95XX Ethernet interface appear.
4. Confirm USB storage devices enumerate.
5. Check the interface MAC, carrier, DHCP and NetworkManager separately.
6. Load both original Diretta modules without force options and capture
   the exact `dmesg` response.
7. Confirm USB audio and the Diretta audio bridge.

A successful build is not proof of successful hardware operation or private
Diretta ABI compatibility.
